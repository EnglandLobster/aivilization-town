根因判断

当前差距不是单个 bug，而是系统演进阶段导致的结构性未闭环。

为什么“很多能力有了，但还不能说完成论文”？

  • 机制边界先行，端到端场景不足 包边界和测试很完整，但大量能力还停留在单元/局部 runner，可证明机制存在，尚未证明长期耦合后仍稳定。
  • 后端内核快于产品表面 API、runtime、trace 已经很丰富，但 web app 基本只是类型契约，用户看不到 town、角色和 steering 流程。
  • 验证框架早于真实数据资产 已经能计算 market stability、heavy-tail、volatility、stratification、ablation，但缺成熟期高频长跑数据和报告产物。

最重要的工程取舍

  • 先补产品闭环，不要只继续加后端切片 没有 UI，steering、profile、trace、市场数据无法被用户理解，反馈回路缺失。
  • 先定义验收 profile，再扩展复杂认知 把 25/100/1000 profile 的 gate 和报告跑实，避免能力越堆越多但无法衡量退化。
  • LLM 层坚持结构化输出和 fallback 当前抽象边界是对的，下一步应补 prompt/eval/trace 数据，不应把自然语言直接塞进 world。

建议推进路线

按“先闭环、再加深、再规模化”的顺序降低长期熵增。

Phase 1

可运行产品切片

把后端能力暴露成一个最小可操作 town 控制台。

  • 投影状态、agent profile、事件流、trace 面板
  • 长目标与短命令 steering 表单
  • 25-agent profile 一键启动和报告
Phase 2

认知闭环补强

把 planning、memory、social 从可用机制推进到可解释行为。

  • LLM strategic / daily / reaction trace 对比
  • 社交对话生成与关系模型联动
  • full replan 替换计划而非只 block
Phase 3

研究级验证

让论文实证指标变成持续生成的 artifact。

  • 100/1000-agent 长跑数据包
  • OHLC、财富分层、轨迹覆盖 dashboard
  • 补 without-objective-decomposition ablation
Phase 4

可玩世界体验

从后台 simulator 变成用户能理解和经营的 AI town。

  • 地图/地点/agent 可视化
  • 用户创建与管理 agent
  • 实时同步、身份、部署、权限
